# 06_E 部門、職務、操作與資料範圍要求

更新：2026-10-27。此文件記錄使用者確認的需求及尚待確認的政策，**不是已完成授權實作或新增正式 DB 模型**。以 D:\2026102001 目前認可版本為基準，沿用 v1.3 PortableAuth 與 ADMIN 既有架構；未知政策先詢問，不自行猜測。

## 使用者已確認的需求

- 部門與職務角色分開，同部門主管與一般同仁可以有不同能力。
- 每個部門可設定功能；檢視、新增、修改、刪除等操作需分開驗證。
- 總經理先跨部門唯讀，修改及核准另議；不能因職稱自動成為全權管理員。
- 使用者已釐清：「個人權限」指使用者所擔任職務角色帶來的權限，職務權限優先於部門權限。本輪不要求另建個別帳號的特例授權模型；不沿用「部門永遠是操作上限」的交集提案。
- 使用者已確認：會有系統管理部門，其中只有被明確指派管理職務／權限者可管理部門、功能與授權，並非全體成員自動有管理能力。具體可管理範圍與可授出權限仍需矩陣核定。
- 使用者已確認：功能操作與資料範圍分別授權。即使職務允許某操作，也不能因此自動存取全公司所有資料。
- 未授權者不能使用功能或存取不屬於其核定範圍的資料；正式功能不以 /dev 作為入口或呼叫來源。
- 開發、驗收與未完成事項必須有紀錄，不能以規劃、示範成功或既有測試冒稱新授權已完成。

## 必須同時驗證的層面

| 層面 | 要回答的問題 |
|---|---|
| 身分及管理站資格 | Session 是否有效？帳號／profile 是否有效？是否可進管理站？ |
| 部門情境 | 選取的是本人有效部門嗎？是否符合核定跨部門例外？切換部門本身不會增加權限 |
| 職務 | 此職務可執行哪些操作？角色來自哪個權威來源？不能信任請求自行聲稱的職務 |
| 功能與操作 | 目標功能是否啟用？這次 view／create／edit／delete 或另核定操作是否允許？ |
| 資料範圍與欄位 | 該筆／該批資料、部門、擁有者及敏感欄位是否在允許範圍？能開頁不等於可看全部列 |
| 授權管理邊界 | 操作者可修改哪些人的部門／功能權限？能否授出該權限？不能藉管理頁自行提權 |

正式路由／service 在伺服器端驗權；選單、按鈕與頁面呈現使用同一授權結果。直接輸入網址、修改 UUID、偽造請求或使用舊快取也必須被檢查。未設定、未知職務、無法取得有效身分／政策或 scope 不明時不放行。

這是安全實作及驗收要求；哪些職務獲准哪些功能，仍須下面的業務矩陣核定。[OWASP Authorization Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html)列出最小權限、預設拒絕、每次請求驗權及越權測試，不能用該原則替代 PM 的業務決策。

## 目前尚缺的共同政策／資料

| 項目 | 當前狀態 | 確認來源 |
|---|---|---|
| 職務清單、角色指派及生效／撤銷來源 | 來源類型已確認是職務角色；實際清單與權威介面尚未提供，v1.3 無完整職務模型 | PM／帳號／整合組 |
| 部門×職務×功能×操作×資料 scope 矩陣 | 使用者要求整理給 PM 核定；操作與資料範圍分別授權，不能由職稱猜內容 | PM／各功能組 |
| 部門、功能目錄、權限管理的操作者與管理範圍 | 限系統管理部門明確獲指派者；具體職務名稱、可管理／可授範圍仍待矩陣 | PM／系統管理責任人 |
| 部門與職務權限優先序、多職務衝突／拒絕解析 | 職務優先於部門已確認；職務未設定時的處理、明確拒絕與多職務衝突仍待核定 | PM／認證及授權整合者 |
| 總經理跨部門可讀資料與欄位 | 只讀原則已確認；具體資料／敏感欄位／匯出仍待核定 | PM／資料功能組 |
| E 管理異動 audit、矩陣集合版本、撤銷即時性接點 | v1.3 未完整提供 | API／DB／整合者 |

原先「部門永遠是操作上限、職務再取交集」的提案已由使用者改為「職務角色優先」，後續不得把原提案實作成正式政策。「個人」在本輪專指職務角色帶來的權限，不是獨立的 user_permissions 特例資料表。v1.3 的當前部門 View 可提供部門基礎權限，仍需按 verified_user_id＋selected_department_id＋function_code 查詢；最終操作決策另依核定職務優先政策，不能只靠此 View 完成，也不能把全域 OR 的其他部門權限直接當成職務授權。

需補充核定職務權限「未設定」時如何處理、明確拒絕如何解析及多職務的合併。資料 scope 已確認獨立授權，具體範圍仍待矩陣。這些語意不由前端勾選值或部門名稱猜測；需共用資料結構時由 API／DB 組提供，E 不自行建立正式授權資料表。

正式授權判斷需涵蓋：有效身分／管理站資格 → 取得權威部門及職務 → 按核定職務優先政策決定操作 → 另外檢查目標資料及欄位 scope → 允許或拒絕。這是待實作的責任分層，不代表缺少矩陣時已可產生最終權限。登入失效或必要政策無法取得時，不因職務名稱放行。

可交給 PM 填寫的矩陣：

| 部門 | 職務 | function_code／功能 | view | create | edit | delete／其他操作 | 資料與欄位範圍 | 可授權範圍 | 核定人／版本 |
|---|---|---|---|---|---|---|---|---|---|
| 待填 | 待填 | 待填 | 待核定 | 待核定 | 待核定 | 待核定 | 待核定 | 待核定 | 待核定 |

未核定欄位不是「允許」或可部署的預設政策。職務指派沿用團隊權威來源，E 不另建平行角色帳冊；若需新增共用資料表，由 API／DB 組處理。

## 尚未執行的越權驗收案例

- 同一部門的主管與一般同仁，依核定矩陣對相同功能產生不同結果。
- 業務使用者更換財務資料 UUID、目標部門或直接呼叫網址／HTTP 操作，沒有該 scope 時拒絕。
- 一人多部門時，其他部門的 edit 不會自動成為職務授權。部門與職務有差異時按職務優先政策解析，並另外驗資料 scope，分別測試允許及拒絕案例。
- 總經理於核定 scope 唯讀，不能修改、刪除、核准或管理帳號／授權，除非另有明確核定。
- 偽造角色／grants／選取部門、無職務、未配置接點、停用／離職及過期 Session 不放行。
- 權限撤銷後下次請求拒絕；列表、詳情、匯出／下載等核定資源均驗資料範圍，不能只檢查某個按鈕。
- 授權管理者不能授出超過其核定可授範圍的權限，也不能藉修改自己取得更高權限。
- 系統管理部門一般成員未獲管理職務／權限時被拒絕；有職務操作權但目標資料不在核定 scope 時仍被拒絕。

以上為未執行清單，只有實作及測試完成後才能改為通過；各功能組仍須在自己的路由／查詢接入共同 guard／scope。

## 開發紀錄與正式安全 audit 分開

每次開發紀錄見 [E-DEVELOPMENT-LOG.md](E-DEVELOPMENT-LOG.md)。正式軟體的授權異動／拒絕操作 audit 另需核定儲存及交易介面，記錄必要的操作者內部識別、動作、目標、結果及政策／版本，不記錄完整請求、密碼、Session／reset Token、金鑰或連線字串。依 [OWASP Logging Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Logging_Cheat_Sheet.html)控制紀錄內容與存取範圍。
