# 部門列表啟停與功能列表精簡

更新：2026/10/29。依使用者與 PM 要求完成，尚未 Commit／Push。

## 操作

1. 登入具部門查看與修改許可的帳號，開啟 /department。
2. 在「編輯／授權功能」右側，啟用／停用欄提供狀態開關。按下後確認，成功才更新狀態；搜尋條件保留。
3. 停用部門仍留在本列表，標示停用，原資料與授權設定保留，可再次啟用。有效工作部門與功能許可來源會排除停用部門。
4. 成員存在不阻擋停用；帳號、公司員工資格、成員歸屬與授權設定均保留。被帳號用作主要部門（含已停用帳號），或未核對的外鍵仍會拒絕停用並顯示原因。主要部門須先經帳號管理調整；本功能不自動搬移成員或繞過 DB 約束。
5. /functions 列表僅保留功能代碼、名稱、適用平台、目錄狀態與操作，移除程式對應整欄。未因此讓未知功能自動取得路由或取消驗權。

## 介面與權限

沿用 POST /department/{department_id}/status：active 為目標布林狀態，新增可選 q 保留搜尋，上限 200 字。原生 form 在沒有 JS 時仍能提交；HTMX 模式使用原生確認視窗、局部回填及送出期間停用按鈕。

維持目前部署邊界、同源、部門修改許可及交易內重驗。查看不代表可修改；直接送 POST 亦驗權。沒有新增 DB 欄位、migration、角色、端點或 JS 相依。

狀態與授權不刪除：重新啟用後依原有功能與成員設定判斷，不新增原本沒有的許可。帳號維護頁中歷史關聯可能保留供處理，不把該歷史顯示當成有效資格。其他未完成接線的業務路由不在本批宣稱完成範圍。

## 同日外鍵誤擋修正

原本「尚未核對 public.department_permissions(department_id)」是程式未認得既有 schema 的誤擋，已修正。正常的 UUID 授權、發票、RAG 與 Session 外鍵不阻擋 is_active 切換，相關資料仍保留；未知／不同欄位組合仍拒絕。使用者後續核定：有效或歷史成員歸屬不阻擋停用，停用只停止該部門權限，歸屬仍保留。主要部門與未知外鍵保護保留；UNASSIGNED 已取消專屬停用限制。核定後 233 項相關離線測試通過，詳見 TEST_REPORT 同日最新紀錄；尚未操作正式 DB 停用。


## UNASSIGNED 操作

UNASSIGNED 與一般部門共用啟停規則。若仍被帳號（包含已停用帳號）設為主要部門，先在該帳號編輯頁勾選適當啟用部門、設為主要部門，再按「儲存部門設定」；帳號本身無須重新啟用。之後返回部門列表停用。成員與歷史資料保留；新增部門正常使用。新帳號請由 /accounts/new 指定啟用部門。
